# MobiFlex Authentication Documentation

Week 1 implementation and learning record

Updated 28 October 2026

## Overview

I implemented the initial authentication flow for MobiFlex using Flutter and Firebase Authentication. Users can register, log in, request a password reset, and log out. The app responds to the current session to display either login or a placeholder home screen.

This records the current implementation, what I learned, the evidence available, and the improvements still needed. The core journeys have been exercised manually; the wider authentication plan and automated test coverage are not complete.

### Implemented features

- Email and password registration with password confirmation.
- Email and password login.
- A separate form for requesting a password reset email.
- Logout from the home screen.
- Session-driven routing and Firebase default session persistence.
- Required-field checks and basic email-format validation.
- Loading messages and guards against repeated form submissions.
- Readable error messages and disposal of text controllers.

### User journeys

- New user: register, reach home, then log out when needed. Registration also signs the user in.
- Returning user: log in, reach home, then log out when needed.
- Forgotten password: request a link, change the password through the email, then return to login.
- Returning session: open or refresh the app; Firebase restores the session and AuthGate selects the screen.

Password reset is an optional recovery journey. It is not a required step between login and logout.

## Code walkthrough

### Application startup

`lib/main.dart`

WidgetsFlutterBinding.ensureInitialized() prepares Flutter before using plugins. Firebase.initializeApp() loads the generated configuration, and await waits for setup to finish before runApp starts MyApp. MyApp builds MaterialApp with the MobiFlex theme and AuthGate as its home.

lib/firebase_options.dart is generated by FlutterFire. DefaultFirebaseOptions.currentPlatform selects configuration for the running platform. The supplied configuration covers Android and web; having other platform folders does not establish that Firebase is configured or tested there.

### Session handling

`lib/screens/auth_gate.dart`

AuthGate listens to FirebaseAuth.instance.authStateChanges() through StreamBuilder<User?>. User? means a Firebase user or null. The stream supplies the initial session state and later sign-in or sign-out changes [1].

| State | Visible result |
| --- | --- |
| Waiting for initial state | A loading indicator. |
| User is present | HomeScreen. |
| No user is present | LoginScreen. |
| Session stream reports an error | A message asking the user to restart. |

This is session handling, not form validation. Validation checks entered values; the gate chooses a screen from the session. Backend data permissions must still be enforced separately.

### Login

`lib/screens/login_screen.dart`

The form checks email format and requires a nonempty password. _submit() stops if validation fails or a request is already running. It then sets _isLoading, disables the submit and navigation buttons, and calls signInWithEmailAndPassword().

If Firebase signs the user in, AuthGate reacts to the session change and shows home. Login does not manually push HomeScreen. If the login screen is still mounted, it clears the password and requests a success snackbar. On failure, it displays a readable message. The finally block resets loading if the screen still exists.

## Registration recovery and logout

### Registration

`lib/screens/register_screen.dart`

The form requires an email, a password, and a matching confirmation. createUserWithEmailAndPassword() creates the account and signs it in. The screen clears both password fields, requests a success snackbar, and calls Navigator.pop().

Registration was opened above login using Navigator.push(). Closing that page reveals the root screen, where AuthGate now displays home. This navigation assumes registration was opened as a pushed page. A different entry point would need a review of that assumption.

### Password reset

`lib/screens/reset_password_screen.dart`

The screen validates the email before calling sendPasswordResetEmail(). The user changes the password through the emailed link [2]. A successful request does not by itself prove delivery or completion of the reset.

The confirmation does not reveal whether an account exists for that email. This differs from checking whether the address has a valid format. The user-not-found error receives the same neutral confirmation.

### Logout

`lib/screens/home_screen.dart`

The logout icon calls FirebaseAuth.instance.signOut(). AuthGate receives the signed-out state and shows login. A failed request displays an error if the screen is still mounted. Logout ends the session; it does not delete the account. The current logout action has no loading guard.

## Credentials and storage

The text controllers temporarily hold the entered email and password. Firebase Authentication manages the account and password verification. The app does not write a password database or implement its own hashing. Password obscuring hides the visible characters; it does not encrypt the controller value.

The Firebase SDK manages saved authentication state. Remaining signed in does not require my code to save the password [1]. An account has a UID that can later associate it with progress or favourites. Those records need separate database storage and access rules.

firebase_options.dart identifies the Firebase project and app; it is not a list of user credentials. Firebase client API keys need appropriate restrictions, while data access relies on the relevant security controls [3].

## What I learned

| Concept | What it means in this implementation |
| --- | --- |
| Form validation | A validator returns an error message for invalid input. Returning null means the field passed validation. |
| TextEditingController | Gives access to entered text. dispose() releases controller resources when the screen is removed. |
| StatefulWidget | A widget whose associated State holds changing values, such as the loading flag. |
| setState() | Updates local state and tells Flutter that the interface needs rebuilding. |
| Future and await | A Future represents an operation that finishes later. await waits within the method without freezing the interface. |
| mounted | Checks whether the State is still attached before using its context or updating it after an asynchronous wait. |
| try catch finally | try runs the request; catch handles failures; finally runs after success or failure and resets loading when mounted. |
| StreamBuilder | Rebuilds part of the interface when a stream emits a new value, such as a changed session. |
| Navigation | push opens another page; pop closes it. MaterialPageRoute<void> declares no meaningful return value. |
| Authentication and authorisation | Authentication identifies the user. Authorisation determines what that user may access. |

### Why these choices were useful

Using one auth gate keeps login and logout destinations consistent with Firebase. Loading guards prevent duplicate form requests. Friendly error mappings avoid showing raw backend messages. mounted checks account for a user leaving the screen while a request is running.

These choices do not replace tests. A success snackbar can be skipped if the gate has already removed the login screen. Fields also remain editable while form requests run in this snapshot, even though submit buttons are disabled.

## Current limitations

- Firebase calls, loading state, and error mapping are inside the screens. The planned repository and controller layers are not implemented.
- Registration only checks that the password is nonempty and the confirmation matches. The main plan specifies at least six characters, an uppercase character, and a special character. Client validation and the live Firebase policy still need aligning; console enforcement was not verified.
- Guest access, guest-account upgrading, account deletion, and email verification are not implemented.
- The current gate requires sign-in to reach home. The wider plan calls for a public or guest experience.
- Private progress storage and its security rules, emulator integration, and automated auth coverage are absent from this snapshot.
- Password visibility controls, autofill hints, keyboard actions, accessibility checks, and wider device testing remain to be added. Firebase startup failures need a recovery experience.
